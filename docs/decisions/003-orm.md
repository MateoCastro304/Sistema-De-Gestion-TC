# ADR-003 — ORM / Query Builder

**Fecha:** 2026-08  
**Estado:** Pendiente de decisión  
**Decisores:** Equipo técnico

---

## Contexto

Con PostgreSQL como base de datos (ver ADR-002), el equipo necesita elegir cómo interactuar con la base desde Node.js/TypeScript. Las necesidades principales son: migraciones versionadas, tipado estático de queries, soporte para relaciones complejas, y queries de reportes.

## Opciones evaluadas

### Opción A: Prisma

ORM moderno con schema declarativo (`schema.prisma`), cliente tipado generado automáticamente, y sistema de migraciones integrado (`prisma migrate`).

**A favor:**
- El cliente generado provee tipado end-to-end: si cambia el schema, el código de TypeScript falla en compilación.
- Migraciones: `prisma migrate dev` genera SQL legible y versionado.
- Curva de aprendizaje baja: el schema es legible para devs sin experiencia previa.
- Excelente integración con NestJS.

**En contra:**
- Queries muy complejas o específicas de PostgreSQL requieren `prisma.$queryRaw`.
- El patrón Active Record no encaja con DDD (Domain-Driven Design); Prisma usa Data Mapper, lo cual es compatible.

### Opción B: TypeORM

ORM con decoradores, más cercano a la filosofía de NestJS por sus raíces comunes.

**A favor:**
- Integración muy natural con NestJS (mismo enfoque de decoradores).
- Soporte para entidades más expresivas.

**En contra:**
- Historial de bugs en migraciones generadas automáticamente: es común que la migración auto-generada sea incorrecta y deba corregirse manualmente.
- Tipos menos seguros que Prisma en algunos escenarios.

### Opción C: Knex

Query builder puro. No genera tipos automáticamente; el dev escribe SQL y Knex provee una API fluida.

**A favor:**
- Máximo control sobre el SQL generado.
- Ideal para queries complejas de reportes.

**En contra:**
- No genera tipos automáticamente: el equipo debe mantener interfaces TypeScript manualmente.
- Más verboso para operaciones CRUD simples.
- No reemplaza la necesidad de un sistema de migraciones separado.

## Recomendación provisional

**Prisma** para la mayoría de las operaciones, con `prisma.$queryRaw` para los reportes o queries específicas de PostgreSQL (como uso de SEQUENCEs o window functions).

## Pendiente para cerrar esta decisión

- [ ] Confirmar experiencia previa del equipo con Prisma vs TypeORM.
- [ ] Evaluar si la complejidad de los reportes justifica agregar Knex como complemento para queries analíticas.
