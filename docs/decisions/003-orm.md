# ADR-003 — ORM / Constructor de consultas

**Fecha:** 2026-08  
**Estado:** Decisión pendiente  
**Responsables de la decisión:** Equipo técnico

---

## Contexto

Con PostgreSQL como base de datos (ver ADR-002-data-base.md), el equipo necesita elegir cómo interactuar con ella desde Node.js/TypeScript. Las necesidades principales son: migraciones versionadas, tipado estático de consultas, soporte para relaciones complejas y consultas de reportes.

## Opciones evaluadas

### Opción A: Prisma

ORM moderno con un esquema declarativo (`schema.prisma`), un cliente tipado generado automáticamente y un sistema integrado de migraciones (`prisma migrate`).

**Ventajas:**
- El cliente generado proporciona tipado de extremo a extremo: si cambia el esquema, el código TypeScript falla durante la compilación.
- Migraciones: `prisma migrate dev` genera SQL legible y versionado.
- Curva de aprendizaje baja: el esquema es legible para desarrolladores sin experiencia previa.
- Excelente integración con NestJS.

**Desventajas:**
- Las consultas muy complejas o específicas de PostgreSQL requieren `prisma.$queryRaw`.
- El patrón Active Record no encaja con DDD (diseño guiado por el dominio); Prisma usa Data Mapper, que es compatible.

### Opción B: TypeORM

ORM con decoradores, más cercano a la filosofía de NestJS por sus orígenes compartidos.

**Ventajas:**
- Integración muy natural con NestJS (el mismo enfoque basado en decoradores).
- Soporte para entidades más expresivas.

**Desventajas:**
- Historial de errores en migraciones generadas automáticamente: es habitual que la migración generada sea incorrecta y requiera correcciones manuales.
- Menor seguridad de tipos que Prisma en algunos escenarios.

### Opción C: Knex

Constructor de consultas puro. No genera tipos automáticamente; el desarrollador escribe SQL y Knex proporciona una API fluida.

**Ventajas:**
- Máximo control sobre el SQL generado.
- Ideal para consultas complejas de reportes.

**Desventajas:**
- No genera tipos automáticamente: el equipo debe mantener las interfaces TypeScript manualmente.
- Más verboso para operaciones CRUD simples.
- No reemplaza la necesidad de un sistema de migraciones separado.

## Recomendación provisional

**Prisma** para la mayoría de las operaciones, con `prisma.$queryRaw` para reportes o consultas específicas de PostgreSQL (como el uso de secuencias o funciones de ventana).

## Decisión

La decisión final es adoptar **Prisma** como ORM principal, usando `prisma.$queryRaw` para casos específicos que requieran SQL personalizado. Las desventajas de Prisma se consideran manejables dado el contexto del proyecto.
