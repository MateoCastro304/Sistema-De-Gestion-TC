# ADR-003 — ORM / Query Builder

**Date:** 2026-08  
**Status:** Decision pending  
**Decision makers:** Technical team

---

## Context

With PostgreSQL as the database (see ADR-002-data-base.md), the team needs to choose how to interact with the database from Node.js/TypeScript. The main needs are: versioned migrations, static query typing, support for complex relationships, and reporting queries.

## Options evaluated

### Option A: Prisma

Modern ORM with a declarative schema (`schema.prisma`), an automatically generated typed client, and an integrated migration system (`prisma migrate`).

**Pros:**
- The generated client provides end-to-end typing: if the schema changes, TypeScript code fails at compile time.
- Migrations: `prisma migrate dev` generates readable, versioned SQL.
- Low learning curve: the schema is readable for devs without prior experience.
- Excellent integration with NestJS.

**Cons:**
- Very complex or PostgreSQL-specific queries require `prisma.$queryRaw`.
- The Active Record pattern doesn't fit DDD (Domain-Driven Design); Prisma uses Data Mapper, which is compatible.

### Option B: TypeORM

ORM with decorators, closer to NestJS's philosophy due to shared origins.

**Pros:**
- Very natural integration with NestJS (same decorator-based approach).
- Support for more expressive entities.

**Cons:**
- History of bugs in auto-generated migrations: it's common for the auto-generated migration to be incorrect and require manual fixes.
- Less type-safe than Prisma in some scenarios.

### Option C: Knex

Pure query builder. Doesn't generate types automatically; the dev writes SQL and Knex provides a fluent API.

**Pros:**
- Maximum control over the generated SQL.
- Ideal for complex reporting queries.

**Cons:**
- Doesn't generate types automatically: the team must maintain TypeScript interfaces manually.
- More verbose for simple CRUD operations.
- Doesn't replace the need for a separate migration system.

## Provisional recommendation

**Prisma** for most operations, with `prisma.$queryRaw` for reports or PostgreSQL-specific queries (such as using SEQUENCEs or window functions).

## Decision

The final decision is to adopt **Prisma** as the primary ORM, using `prisma.$queryRaw` for specific cases that require custom SQL. Prisma's cons are considered manageable given the project's context.
